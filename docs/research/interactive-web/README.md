## 다섯 편을 관통하는 공통 구조

### 1. 인터랙션 모델은 사실상 하나다

01·02·04는 도구와 에셋이 전부 다르지만 **동일한 모델**을 쓴다.

```
문서 스크롤 = 타임라인 스크러버
페이지는 실제로 이동하지 않고(sticky/pinned) 스크롤 진행률이 씬을 구동한다
```

차이는 "무엇을 구동하는가"뿐이다.

| 영상 | 구동 대상 | 비용 | 의존성 |
| --- | --- | --- | --- |
| 01 | 사전 렌더 MP4의 재생 위치 | AI 크레딧(≈800) + 영상 용량 | FFmpeg, Higgsfield |
| 02 | 사전 렌더 MP4 + 진행 바 UI | AI 크레딧 + 영상 용량 | Seedance |
| 04 | three.js 씬의 실제 3D 모델 | 모델 생성 1회 | three.js, GLB |
| — | **CSS/SVG 씬** | **0** | **없음** |

마지막 행이 중요하다. **인터랙션 모델 자체에는 AI 에셋도 3D 라이브러리도 필요 없다.** 에셋은 화려함의 문제이지 구조의 문제가 아니다.

### 2. 연속성이 품질을 만든다

- 01: 앞 영상의 **마지막 프레임을 다음 영상의 첫 프레임으로** 재사용 → 컷이 안 보임
- 02: 4개 분할 영상은 일관성이 깨졌고, **완성 상태를 레퍼런스로 준 20초 단일 영상**으로 해결
- 04: 씬 1 → 씬 2 전환을 "글자가 흩어져 날아간다"는 **하나의 물리적 동작**으로 연결

세 사례 모두 결론이 같다 — **끝 상태를 먼저 고정하고, 경계를 지운다.**

### 3. 레퍼런스 없이 만들면 AI 티가 난다 (03)

과한 자간, 습관적 그라디언트, 밝은 배경, 특정 초록 계열 + 카드 그라디언트, 불필요한 border. 지시 없이 생성하면 정확히 이것들이 나온다. 회피 방법은 레퍼런스·스크린샷·명시적 스타일 지시뿐이다.

### 4. 05번은 나머지 넷의 품질 게이트다

01~04는 "무엇으로 만드는가", 05는 "왜 좋아 보이는가"를 다룬다. **화려한 스크롤 인터랙션을 붙여도 히어로에 CTA와 증거가 없으면 전환은 일어나지 않는다.** 순서상 05를 먼저 적용하는 것이 맞다.

## 이 저장소의 제약 조건

적용안을 고를 때 반드시 함께 고려해야 하는 것들이다.

- `next.config.mjs`의 `output: "export"` — **완전 정적**. 서버 액션·미들웨어·런타임 라우트 핸들러 사용 불가(`README.md`의 발행 규칙에 명시).
- 배포 대상은 GitHub Pages — 대용량 영상 에셋은 저장소 용량과 초기 로딩에 직접 영향을 준다.
- 현재 런타임 의존성은 `next`, `react`, `react-dom`, `zod`, `@next/mdx`뿐. **애니메이션 라이브러리가 하나도 없다.**
- 접근성 장치가 이미 갖춰져 있다 — `prefers-reduced-motion` 대응, `MotionControl` 수동 정지 버튼, `data-motion="paused"` 훅. 새 모션은 반드시 이 체계에 편입되어야 한다.
- 모든 공개 콘텐츠는 **한국어·영어 쌍**이 필요하다.
- 배포 전 `type-check` → `lint` → `build`(콘텐츠 검증 포함) → Playwright E2E를 통과해야 한다.

## 적용 옵션

### A. 에셋 0원 — CSS/JS 스크롤 타임라인 + 05번 원칙 적용

- 05번 7원칙으로 히어로 재설계(CTA·증거 추가), 대비 구조 정리
- `position: sticky` 씬 + 스크롤 진행률 바인딩으로 01/02/04의 인터랙션 모델 구현
- 기존 `flow-machine`, `capability-crawler`를 자동 반복에서 **스크롤 구동**으로 전환
- 문자 분해 전환(04)을 기존 `KineticType`에 결합
- 비용 0, 의존성 0, 용량 0. `prefers-reduced-motion`에서 완전 정지 가능

### B. A + 자체 제작 프레임 시퀀스

- 03번의 "MP4 → JPEG 시퀀스" 기법으로 스크럽 성능 확보
- 씬을 직접 렌더(SVG/Canvas)해 WebP 시퀀스로 굽는 방식이면 AI 크레딧 없이 가능
- 용량 관리 필요

### C. A + AI 생성 에셋 (01/02 방식 그대로)

- Higgsfield 크레딧 필요(참고: 6씬 데스크톱 기준 803크레딧 / 약 2시간)
- 저장소 용량, 초기 로딩, 모바일 데이터 사용량 검토 필요

### D. A + three.js GLB 히어로 (04 방식)

- 런타임 의존성 추가(three.js). 히어로 한 곳으로 제한 + 동적 import + 정적 폴백 필요
- tone mapping 이슈를 사전에 지시해야 함

**권장**: A를 먼저 완료해 구조와 품질 게이트를 확보한 뒤, 그 위에 B/C/D 중 하나를 얹는다. A는 그 자체로 완결되며 이후 어떤 선택을 하든 버려지지 않는다.

## 진행 상태

- **A안 완료** — 스크롤 구동 씬 시퀀스로 홈을 전면 재구성했고 05번 원칙을 적용했다. [06번 문서](./06-portfolio-implementation.md) 참고.
- **C안 대기** — AI 영상 에셋은 Higgsfield 크레딧이 0(free 플랜)이라 아직 생성하지 않았다. 씬마다 영상 슬롯을 비워 두었으므로, 크레딧이 생기면 `public/scroll-world/`에 파일을 넣고 `lib/scroll-world.ts`에 경로만 추가하면 된다.
- **Pitch-AC 반영** — 아직 시작하지 않았다.
