# 01. scroll-world 스킬로 만든 스크롤 3D 랜딩 페이지

- **영상**: [한 달 만에 GitHub 스타 7.7k | 스킬 하나로 만든 애플급 3D 페이지](https://www.youtube.com/watch?v=KpH_ThmwBAw)
- **채널**: 후츠릿 - AI 자동화로 삽질 줄여주는 개발자 (`@chutzrit`)
- **저장소**: https://github.com/oso95/scroll-world
- **한 줄 요약**: 스크롤이 "미리 렌더된 카메라 비행 영상"의 재생 위치를 조종하게 만들어, 3D 엔진 없이 애플 제품 페이지 같은 몰입형 랜딩을 만든다.

## 핵심 원리 — 실시간 3D가 아니다

가장 중요한 통찰이자 이 영상 전체의 뼈대다.

> 이 페이지는 웹이 화면을 실시간으로 그리는 게 아니다. 코드가 할 수 있는 건 모션을 주는 것뿐이지, 없던 장면을 만들어내지는 못한다.

따라서 구조는 이렇게 뒤집힌다.

1. 카메라가 장면 속으로 날아 들어가는 **영상을 미리 생성**한다.
2. 웹페이지는 그 영상의 **재생 위치(playhead)를 스크롤에 연결**하기만 한다.
3. 스크롤 다운 → 정방향 재생, 스크롤 업 → 역방향 재생.

즉 **영상 재생 바를 방향키가 아니라 스크롤로 조작하는 방식**이다. 진입 시점에는 첫 프레임에서 정지해 있다.

## 컷 없는 씬 연결 — 마지막 프레임 재활용

여러 영상을 이어 붙이면 보통 경계에서 티가 난다. scroll-world는 이 문제를 이렇게 푼다.

```
영상 A: [f0][f1]...[f_last]
                      ↓ FFmpeg으로 마지막 프레임 추출
영상 B: [f_last][f1]...[f_last']   ← 추출한 이미지를 다음 영상의 "시작 이미지"로 사용
```

앞 영상의 끝 프레임과 다음 영상의 시작 프레임이 **픽셀 단위로 동일**하므로 이어 붙여도 컷이 보이지 않는다. 이 프레임 추출과 웹 재생용 변환을 FFmpeg이 담당한다.

## 준비물

| 구분 | 도구 | 역할 |
| --- | --- | --- |
| 필수 | Higgsfield (CLI 또는 MCP) | 장면 이미지 · 카메라 비행 영상 생성 |
| 필수 | FFmpeg | 마지막 프레임 추출, 웹 재생용 인코딩 |
| 선택 | Python + Pillow | 모바일 세로 버전, 장면 이미지 배경 투명 처리(누끼) |
| 선택 | Codex CLI | 장면 이미지를 Higgsfield 대신 생성해 크레딧 절감 |

- 코딩 에이전트는 이미지·영상 생성 능력이 없으므로 생성 도구 연결이 필수다.
- 영상 생성은 Higgsfield만 가능하다. Codex는 영상의 **소스가 되는 장면 이미지**까지만 만들 수 있다.
- 영상에서는 CLI 미설치 상태에서 **MCP 서버로 대체 가능**함을 확인했다.
- `SKILL.md` 형식을 지원하는 에이전트라면 Claude Code, Codex 어디서든 사용 가능하다.

## 진행 순서

1. **인터뷰** — 어떤 산업인지, 핵심 메시지가 뭔지, 씬 순서를 어떻게 할지 질문한다.
2. **크레딧 견적 · 승인** — 에셋 생성 전에 예상 비용을 보여주고 승인을 받는다. 실제 돈이 나가기 전에 확인할 수 있다.
3. **에셋 생성** — 장면 이미지 → 카메라 비행 영상.
4. **페이지 조립** — 생성된 에셋을 연결해 랜딩 페이지로 만든다.

사용자가 하는 일은 **질문에 답하고 승인하는 것뿐**이며, 코드는 한 줄도 쓰지 않는다.

## 단계적 승인 구조 (비용 통제 장치)

전체 일괄 승인은 리스크가 크므로 단계를 쪼갠다.

```
씬 구성 제안 → 씬 1의 스틸 1장만 생성(11크레딧) → 확인
  → 나머지 5장 이미지 생성 → 확인
  → 드래프트(720p) 영상 → 확인
  → 본 렌더
```

영상에서는 드래프트를 건너뛰려 했으나, 에이전트가 **드래프트의 목적은 씬 확인이 아니라 카메라 움직임과 이음새 확인**이라고 정정한다. 마지막 프레임 → 다음 시작 프레임 연결이 성립하는지 먼저 검증해야 하기 때문이다.

## 실제 비용과 시간

- 총 소요: **803 크레딧 / 약 2시간 10분** (6씬 구성, 데스크톱 기준)
- 단가
  - 장면 이미지: **7 크레딧/장**
  - 씬 영상: **72 크레딧/개** (총 7개 = 재작업 1건 포함)
  - 씬 연결(커넥터) 영상: 씬 6개 기준 **5개** 추가 생성
  - Seedance 2.0 mini: 4 크레딧 (이음새 기술 테스트용)
- 영상 1개 생성에 약 5분, 6개에 약 30분. **작업 시간의 대부분은 대기 시간**이고 사람이 개입하는 시간은 매우 짧다.
- 모바일/데스크톱 동시 제작은 크레딧이 2배. 영상에서는 데스크톱만 만들고 모바일은 반응형 프레임 조정으로 처리했다(모바일 전용 영상을 새로 만든 것이 아님).

## 실전에서 얻은 판단

- **아트 디렉션**: 기본값은 디오라마 스타일. 씬 이동 방식도 선택 항목이다.
- **톤 조정이 가독성을 좌우한다**: 초기 결과가 화이트 배경이라 웹에 올렸을 때 너무 밝아 눈에 안 들어왔다. VS Code Material 테마 톤(어두운 계열)으로 다시 요청해 해결했다.
- **여정 구성은 시작과 끝만 정해도 된다**: "개발자 책상에서 시작해서 강의실에서 마무리"라는 추상적 입력만으로 6개 씬 스토리를 구성해 준다.
- 마음에 안 드는 씬은 개별 재생성(7크레딧)으로 교체 가능하다.
- 사람이 정지해 있어 어색한 영상 1개만 골라 재생성했다 — **부분 재작업이 가능한 구조**.
- 씬 사이를 연결할 때 에이전트가 의미적 맥락을 파악해 중간 연결 영상(예: 빌딩 전경)을 추가로 만들어 준다.
- 완성 후 PC/모바일 각각 자체 검증까지 수행한다.

## 이 포트폴리오에 옮길 수 있는 것

- **"스크롤 = 타임라인 스크러버"라는 인터랙션 모델** 자체는 에셋 종류와 무관하다. 비디오 대신 CSS/SVG 씬을 스크롤에 물려도 동일한 체감을 만들 수 있다.
- **씬 간 무결 연결(마지막 프레임 = 다음 첫 프레임)** 원칙은 섹션 전환 설계에 그대로 쓸 수 있다. 섹션이 바뀔 때 화면이 "잘리지" 않고 이어지게 만든다.
- **단계적 승인 / 비용 견적 우선** 워크플로는 이 저장소의 검증 우선 원칙(`README.md`의 발행 규칙)과 결이 같다.
- 주의: 실제 영상 에셋 도입 시 정적 배포(GitHub Pages) 용량과 초기 로딩 비용을 반드시 계산해야 한다.
